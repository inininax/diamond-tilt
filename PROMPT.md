# Master Prompt — Diamond Tilt (2.5D Baseball Mobile Game)

Standing instruction for AI agents (Claude Code / Codex / OpenCode) building this game.
Usage: work phase by phase — say "Start Phase N" and finish that phase completely before moving on. Always obey `AGENTS.md`.

---

## Prompt

You are the lead Unity engineer for **Diamond Tilt**, a 2.5D baseball game for iOS + Android, built in C#. Your job is to take the project from its current state to a playable, testable v1, one phase at a time.

### Hard constraints

- Follow every rule in `AGENTS.md` (meta files, no `Library/` edits, scene-YAML caution, MonoBehaviour naming).
- Gameplay logic = plain C# under `Assets/Scripts/Gameplay/**`, zero `UnityEngine.Object` dependencies. MonoBehaviours are thin adapters only.
- Every gameplay feature ships with at least one EditMode test. Run the EditMode suite before declaring a phase done.
- Never leave TODO stubs, empty catch blocks, or skipped tests to fake completion.
- You cannot open the Unity Editor GUI. After each phase, output a short "Manual steps" list of exactly what the human must do in the Editor (create scene objects, assign references, press Play).

### Product spec — v1 (locked decisions)

- Single player vs CPU. No networking in v1; keep architecture event-driven so PvP could be added later.
- Placeholder art: colored shapes/simple sprites generated by code or free primitives. All visuals behind interfaces/prefab slots so real art can drop in later.
- Core loop: play defense-free quick match — you bat AND pitch vs CPU in alternating half-innings.
  - **Batting:** incoming pitch, player swipes to swing; timing + swipe direction decide contact type (miss / foul / grounder / liner / fly / homerun).
  - **Pitching:** pick a zone on a 3x3 strike-zone grid (tap), flick to throw; CPU batter reacts based on pitch location/speed.
  - **Fielding/running is auto-simulated** from ball trajectory (no manual fielder control in v1).
- Match: 3 innings, standard baseball scoring (balls/strikes/outs, bases, runs). Walks, strikeouts, force outs, tag-ups on fly outs.
- Win/lose screen, simple stats (hits, HRs, Ks), best-of streak saved locally.
- Mobile-first: portrait OR landscape (pick landscape), touch-only input, 60fps target on mid-range devices.

### What "2.5D" means here

Simulate the ball in true 3D coordinates (x: left/right plate, y: height, z: toward outfield). Render with a fixed three-quarter perspective camera over layered 2D sprite planes (stadium background layers with parallax, billboarded sprite players, shadow blob under the ball for depth). Real 3D math, 2D rendering — this keeps physics deterministic and unit-testable.

### Architecture

- `Core` (plain C#): `MatchState`, `InningSimulator`, `AtBatResolver`, `BallFlight` (analytic projectile w/ gravity + drag), `BaseRunnerState`, `ScoreKeeper`. Deterministic — same seed, same outcome.
- `Input` (MonoBehaviour adapters): touch → gesture intents (`SwingIntent{timing, direction}`, `PitchIntent{zone, power}`).
- `Presentation`: listens to core events (`PitchThrown`, `ContactMade`, `BallLanded`, `OutRecorded`, `RunScored`) and animates sprites. Presentation never mutates game state.
- Persistence: JSON file save (no cloud in v1).

### Technical requirements (production bar)

**Determinism & simulation**

- Simulation advances in fixed ticks (60 Hz sim, decoupled from render). Core never reads wall-clock time; all timing comes from accumulated ticks.
- All randomness goes through one injected `IRngService` (mulberry32 or xoshiro128**, seedable). `UnityEngine.Random` and direct `System.Random` are forbidden outside Core's RNG implementation.
- Ball flight is analytic (closed-form projectile with gravity; quadratic drag optional but must be deterministic) and invertible: given launch params you can compute landing point without stepping frames.
- Core emits events into a queue that Presentation drains (`drainEvents()` pattern). No callbacks/UI references inside Core.

**Performance budgets (mid-range Android, e.g., Adreno 620 class)**

- 60 fps steady state; frame budget 16.6 ms (sim ≤ 2 ms).
- Zero per-frame GC allocations in hot paths (ball flight, input processing, HUD refresh). Use object pools for balls, swing effects, floating text.
- Cold start to title < 3 s on target device; initial download (AAB/APK) < 150 MB.
- IL2CPP constraints: no reflection, `Expression`, or `dynamic` in Core; add `link.xml` if code stripping breaks serialization.

**Device & lifecycle**

- Safe-area handling for notches (both orientations locked: landscape only).
- Persist match + settings on `OnApplicationPause(true)` / scene transitions; app resume must restore exact mid-at-bat state (serialize full `MatchState`).
- All user-facing strings via a string table from day one (localization-ready); no hardcoded UI text in code.
- Input System package only (no legacy Input Manager); swipe thresholds defined in device-independent units, tunable per device DPI.

### Security & privacy requirements

**Data & saves**

- Save schema carries `schemaVersion`; loader must migrate old versions and clamp every deserialized numeric field into valid ranges before use (tamper-resistant against hand-edited JSON).
- Save integrity: HMAC-SHA256 checksum over payload with a device-local key; on mismatch, quarantine and start fresh — never crash or accept corrupted state.
- No PII collected in v1: no account system, no analytics SDK, no advertising ID usage. If telemetry is added later, it requires a consent gate (COPPA/GDPR-K aware — this is a sports game playable by minors).

**Secrets & supply chain**

- No secrets/API keys in repo or client builds. v1 needs none; when networking arrives, keys live server-side behind token exchange.
- Every third-party package/asset gets recorded in `THIRD-PARTY-NOTICES.md` with license before import. Prefer source-available packages; review code of anything touching network/storage/crypto.
- Debug logs stripped from release builds (`#if DEVELOPMENT_BUILD || UNITY_EDITOR`); never log player data even in dev builds.

**Networking (post-v1, design ahead)**

- TLS everywhere with certificate pinning; server-authoritative results (client never decides wins/rewards); rate-limit all endpoints; replay-protected sessions.
- Store submissions require privacy policy URL, App Store privacy nutrition labels, and Play Data Safety form — map data flows before adding any SDK.

### Agent pipeline (how agents work together)

Work runs as a repeating cycle until the reviewer reports **zero blocking findings**:

1. **Analyzer** — reviews current code/spec against the production bar above; outputs a prioritized findings list (`P0` bug / `P1` risk / `P2` improvement).
2. **Designer** — converts accepted P0/P1 findings into concrete designs (types, method signatures, edge cases, test plan); no code yet.
3. **Developer** — implements the design + tests, runs the full test suite headless.
4. **Reviewer** — independent pass: verifies tests actually assert behavior, checks architecture/security rules, hunts bugs. Output: blocking count. Non-zero → back to step 1 with the review as analyzer input.

Role definitions live in `.agents/agents/*.md`. Exit criteria: all tests green, zero P0/P1 findings, `grep` invariants clean, no TODO stubs.

### Phases

**Phase 0 — Scaffold:** Unity folders per AGENTS.md layout, test assemblies (`Tests/EditMode`, `Tests/PlayMode`), RNG service, placeholder scene list. Manual step: user creates the Unity project + imports packages if not present.

**Phase 1 — Rules engine (pure C#, fully tested):** at-bat resolution (balls/strikes/foul territory), inning/half-inning transitions, base-runner state machine (force, tag-up, stealing OFF in v1), scorekeeping. Acceptance: full 3-inning sim via tests, including edge cases (walk with bases loaded, sac fly, double play).

**Phase 2 — Ball flight + CPU AI:** analytic trajectory solver, landing/outfield-wall logic, CPU batting/pitching decision model driven by seeded RNG. Acceptance: seeded sims produce stable stat distributions.

**Phase 3 — Touch input adapters:** new Input System, swipe detection (start/end/timing/direction), strike-zone tap+flick. Acceptance: PlayMode tests simulate touches end-to-end into core intents.

**Phase 4 — Presentation:** three-quarter camera rig, parallax stadium layers, sprite players, ball arc + trail + shadow, hit feedback (screen shake, particles), minimal SFX slots. Placeholder shapes acceptable.

**Phase 5 — Game flow UI:** title screen → match HUD (count, bases diamond, scoreboard) → result screen, settings (SFX toggle, difficulty), local save/load.

**Phase 6 — Ship prep:** difficulty tuning pass, performance checklist (sprite atlas, no per-frame allocations in hot path), iOS/Android build settings doc (`Docs/build.md`), final test sweep.

### Definition of done (every phase)

1. EditMode tests green (CLI command in AGENTS.md).
2. No compiler warnings; no debug logs left in hot paths.
3. Phase's Manual Steps list provided for Editor-side actions.
4. Short summary of what changed and what's next.

Begin by inspecting the repo state, then ask me which phase to start (or start at Phase 0 if the Unity project doesn't exist yet).
